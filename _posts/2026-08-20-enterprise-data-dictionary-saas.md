전통적인 SI에서 표준용어사전과 메타데이터 시스템은 거의 모든 대형 프로젝트에 있었다. 그리고 거의 모든 프로젝트에서 오픈 2년 뒤엔 아무도 안 봤다. 지금 SAP·Salesforce·OutSystems가 섞인 환경에서 "전사 공통 딕셔너리를 만들자"는 얘기가 다시 나오는데, 예전 방식 그대로 하면 결과도 그대로다.

결론부터.

- 전통 표준사전은 **DB를 우리가 만든다**는 전제 위에 있었다. SaaS 조합에서는 그 전제가 깨진다.
- 목표를 **"세 시스템이 같은 이름을 쓰게 한다"에서 "세 시스템 사이를 오가는 데이터가 같은 의미로 번역된다"로 재정의**해야 한다.
- 산출물의 90%는 단어 목록이 아니라 **매핑 테이블**이 된다.
- 강제 지점은 시스템 내부가 아니라 **인터페이스 경계**로 옮긴다.
- 원본은 Git의 YAML, 배포물은 단일 HTML, 갱신은 **LLM 제안 + 사람 승인**.

마지막에 [동작하는 프로토타입](/demo/enterprise-dictionary.html)을 붙여뒀다.

## 1. 전통 SI의 표준용어사전은 어떻게 동작했나

핵심은 한 문장이다. **컬럼명을 사람이 짓지 못하게 만드는 것.** 3단 구조로 조립한다.

**표준단어 사전** — 의미의 최소 단위를 등록한다.

- 고객 → `CUST`, 계좌 → `ACCT`, 거래 → `TRSC`, 금액 → `AMT`
- 동의어(액수, 금액)는 금지어로 지정해 하나만 남긴다

**표준도메인** — 마지막 단어(분류어)가 타입을 결정한다.

- `~금액` → `NUMBER(18,2)`, `~여부` → `CHAR(1)` 'Y/N', `~일자` → `CHAR(8)`
- 컬럼명만 보면 자료형이 결정되므로 설계자가 타입을 임의로 못 정한다

**표준용어** — 단어를 조합해 실제 컬럼명을 만든다. 고객계좌거래금액 → `CUST_ACCT_TRSC_AMT`.

메타데이터 시스템은 이 사전을 저장하고 다음을 수행했다.

- 신규 용어 **신청 → DA(데이터 아키텍트) 승인 → 등록** 워크플로우
- 모델링 툴(ERwin, DA#)과 연동해 DDL 자동 생성
- 운영 DB를 리버스 엔지니어링해 **표준 준수율** 리포트 산출
- 테이블·컬럼 간 영향도와 계보 조회

준수율 95% 이상 같은 수치가 검수·감리 항목으로 계약에 박히는 경우가 많았다.

### 작동한 부분

- 물리 DB 레벨의 명명 일관성은 실제로 확보된다. 처음 보는 테이블도 컬럼명을 읽을 수 있다는 건 큰 자산이다.
- 승인 절차가 있으니 "고객번호"가 5개 이름으로 난립하는 사태는 줄어든다.
- 감리·검수의 객관적 기준으로는 확실히 기능했다.

### 어긋난 부분

| 증상 | 내용 |
|---|---|
| 약어 지옥 | Oracle 30자 제한 시절의 축약 관행이 남아 `CUST_ACCT_TRSC_HIST_SN` 같은 이름이 양산됐다. 결국 사전을 찾아봐야 읽힌다 |
| 사전 비대화 | 단어가 수천 개로 불어나며 유사 단어 통제에 실패. 사전 자체가 관리 대상이 됨 |
| 승인 병목 우회 | 일정 압박 시 승인을 안 기다리고 임시 컬럼을 만든 뒤 정리하지 않음 |
| 숫자 맞추기 | 준수율을 맞추려고 오픈 직전 사전에 단어를 역으로 추가해 100%를 만듦. **지표는 달성되고 표준은 무너진다** |
| 운영 단계 방치 | 구축 종료 후 갱신되지 않아 실제 DB와 불일치 → 신뢰를 잃고 아무도 조회하지 않음 |
| 레이어 단절 | 통제 범위가 DB에 한정되어 Java 변수명, API 필드명, 화면 항목명은 제각각. 매핑 비용은 그대로 |
| 차세대마다 리셋 | 이전 사전을 이관하지 못하고 새로 만드는 일이 반복 |

패턴이 하나다. **강제 장치(감리·검수·승인)가 살아있는 구축 기간에만 규율이 작동하고, 그 장치가 사라지는 운영 단계에서 붕괴한다.** 지금의 데이터 카탈로그나 dbt 계열 도구가 같은 문제를 "사후 승인" 대신 "코드와 함께 버전 관리"로 다시 푸는 것도 이 실패 경험 때문이다.

## 2. LLM 시대: 메타데이터는 대체된 게 아니라 필수 입력이 됐다

"LLM으로 메타데이터 관리"는 하나가 아니다. 방향이 반대인 두 흐름이 섞여 있다.

<pre class="mermaid">
flowchart LR
    subgraph A[A. LLM이 메타데이터를 만든다]
      A1[컬럼 설명 자동 생성] --> A2[용어-물리컬럼 매핑 제안]
      A2 --> A3[품질 룰 초안]
    end
    subgraph B[B. LLM이 메타데이터를 쓴다]
      B1[text-to-SQL] --> B2[카탈로그 챗봇]
      B2 --> B3[MCP로 정의·계보 공급]
    end
    A --> M[(메타데이터)]
    M --> B
</pre>

업계 평가가 갈리는 지점이 정확히 A와 B다.

### A(생성): 대체로 성공 — 기대치가 낮았던 곳에서

- Databricks는 기능 출시 후 Unity Catalog 테이블 메타데이터 업데이트의 **80% 이상이 AI로 작성**된다고 밝혔다.
- 사내 카탈로그에 RAG 방식으로 설명을 생성한 연구에서는 생성된 설명의 **87~88%가 데이터 스튜어드에게 그대로 승인되거나 소폭 수정으로 통과**됐다.

즉 **"아무 설명도 없던 빈칸"을 채우는 일은 확실히 풀렸다.** 1장에서 본, 운영 단계에서 아무도 갱신 안 해 죽어버리던 메타 시스템의 가장 큰 실패 원인 하나가 해소된 것이다.

다만 한계선이 명확하다.

- 본질적으로 모호한 컬럼에서는 모델이 여전히 헤맨다. `CUST_STAT_CD`의 값 `03`이 "휴면"인지 "해지대기"인지는 **스키마에 없다.**
- 평가 자체가 미덥지 않다는 지적도 있다. LLM을 심사자로 쓰면 사람이 쓴 메타데이터가 더 나은 상황에서도 LLM 스타일 문장을 체계적으로 선호할 수 있다. **"그럴듯한 설명"과 "맞는 설명"의 구분이 지표에서 흐려진다.**

### B(소비): 여기서 실패가 많이 났고, 그게 역설적으로 메타데이터를 살렸다

숫자가 꽤 냉정하다.

| 관측 | 수치 |
|---|---|
| Spider 2.0 (실제 기업 스키마) | 프런티어 모델도 **17~21%** (기존 Spider는 91%) |
| Salesforce 프로덕션 text-to-SQL 에이전트 | 출시 시점 효과성 약 **50%**, 80%에 도달하려 프롬프트당 후보 쿼리 10개 생성 |
| 오류의 성격 | 구문 오류보다 스키마·의미 수준 실패가 **약 81%**. 쿼리는 정상 실행되고 숫자만 틀림 |

그런데 **컨텍스트를 주면 그래프가 급격히 꺾인다.**

- Bayer 내부 데이터 60개 질의에서 GPT-4는 스키마만 줬을 때 **8.3%**, 비즈니스 컨텍스트 문서를 함께 줬을 때 **78.3%**를 기록했다. 스키마 범위만 좁히는 것으로는 이 효과가 안 나왔다.
- dbt Labs의 2026 벤치마크에서 Sonnet 4.6은 text-to-SQL 90.0% → 시맨틱 레이어 98.2%, GPT-5.3-Codex는 84.1% → 100%로 올라갔다.

가장 중요한 관찰은 정확도가 아니라 **실패 모드**다. 시맨틱 레이어의 실패는 "답할 수 없다"는 에러로 나타나고, text-to-SQL의 실패는 **태연하게 틀린 숫자를 내놓는다.** 감사·규제 대상 업무에서는 이 차이가 정확도 8%p보다 훨씬 크다.

### 그래서 현재 합의

**"LLM이 메타데이터 관리를 대체한다" → 거의 폐기된 관점.** 2023~24년엔 "LLM이 카탈로그를 대체할 것"이라는 주장이 있었지만 지금은 반대로 정리됐다. 메타데이터가 LLM을 위한 필수 입력이 됐다.

**"LLM이 메타데이터를 채우고, 메타데이터가 LLM을 통제한다" → 현재 합의.** 생성은 자동화하되 승인은 사람이, 소비는 시맨틱 레이어를 경유해서.

남은 진짜 병목은 예전과 같다. 한 논평은 dbt 벤치마크를 두고 **진짜 문제는 text-to-SQL이냐 시맨틱 레이어냐가 아니라 시맨틱 모델을 어떻게 생산하고 유지하느냐**이며, 답이 "소수 전문가의 영웅적 수작업"이라면 데모에서는 되고 운영에서는 썩는다고 지적했다.

1장의 실패 패턴과 **구조가 똑같다.** 다만 이번엔 두 가지가 다르다.

1. 사전 갱신 비용이 LLM으로 크게 떨어졌다.
2. **메타데이터가 틀리면 사람이 불편한 게 아니라 AI가 틀린 답을 낸다.** 방치의 대가가 즉시 눈에 보이는 형태로 바뀌었다.

과거 준수율 95%가 감리 항목이었다면, 지금 지표는 "이 에이전트가 낸 매출 숫자가 재무팀 숫자와 같은가"다. 숫자 맞추기로 우회하기는 훨씬 어려워졌다.

> **유보.** 위 벤치마크 수치 상당수가 시맨틱 레이어를 파는 벤더(dbt, Omni, Atlan) 쪽에서 나온다. 방향성은 독립 연구(Spider 2.0, Bayer 사례)와 일치하지만 절대 수치는 각 사의 평가 방법론에 따라 다르게 잡힌다.

## 3. SaaS 혼재 환경: 통제할 수 있는 게 다르다

여기서 본론. SAP·Salesforce·OutSystems에 같은 딕셔너리를 쓰는 게 옳은가?

**방향은 맞다. 다만 "같은 딕셔너리"를 예전 SI 방식대로 정의하면 거의 확실히 실패한다.**

기존 표준사전은 *생성형(prescriptive)* 이었다. 사전이 먼저 있고 → DDL이 그로부터 나오고 → 준수율로 검사. 이게 성립한 이유는 **DB를 우리가 만들었기 때문**이다. 세 시스템 조합에서는 이 전제가 깨진다.

| 대상 | 물리명 통제력 | 현실 |
|---|---|---|
| **SAP 표준** | 0% | `KUNNR`, `BUKRS`, `VBELN`은 절대 못 바꾼다. 손대는 순간 표준 트랜잭션과 업그레이드가 깨진다 |
| **SAP Z-객체/확장필드** | 높음 | 여기만 통제 가능 |
| **Salesforce** | 중간 | 생성 시점엔 자유롭지만, 운영 중 필드의 API명 변경은 Apex·Flow·수식·리포트·연동을 연쇄로 깬다 |
| **OutSystems** | 높음 | 사실상 유일한 그린필드 |

**"세 시스템의 컬럼명을 통일한다"는 목표는 시작하자마자 폐기해야 한다.** 이걸 붙들면 SAP는 예외 처리하고, Salesforce는 마이그레이션 지옥에 빠지고, OutSystems만 규칙을 지키다가 프로젝트가 흐지부지된다.

### 대신 계층을 나누고, 개념 계층만 공유한다

<pre class="mermaid">
flowchart TB
    C["개념 Canonical 계층 · 공유 · 정의/소유 도메인/허용 코드값/계산 규칙"]
    M["매핑 계층 · 핵심 산출물 · 변환 규칙/코드값 대응표/유효기간/소유자"]
    C --- M
    M --- S1["SAP 물리 · Z-객체만 통제"]
    M --- S2["Salesforce 물리 · 신규 필드만 통제"]
    M --- S3["OutSystems 물리 · 전면 적용"]
</pre>

개념 계층에는 **물리 이름이 없다.** 시스템 중립이다. 매핑 계층이 `Customer.id ← SAP KNA1.KUNNR / SFDC Account.Id / OSS Customer.Id`를 붙든다.

즉 **딕셔너리의 성격이 "명명 규칙"에서 "매핑 자산"으로 바뀐다.**

### 실제로 아픈 건 이름이 아니다

이 유형의 프로젝트가 착각하는 지점이 여기다. 명명 통일을 목표로 잡으면 정작 비싼 문제를 안 건드린다.

**문제 1 — 동일 엔티티 식별.** 같은 회사가 SAP엔 `KUNNR=0001234`, Salesforce엔 `Account 001xx`, OutSystems엔 별도 시퀀스로 존재한다. 이건 딕셔너리 문제가 아니라 **MDM(마스터 데이터 관리)** 문제다. 정답은 사전이 아니라 **Global ID + 크로스레퍼런스 테이블**이다. 이걸 빼놓고 사전만 만들면 "이름은 같은데 어느 게 같은 고객인지는 모르는" 상태가 된다.

**문제 2 — 코드값과 상태 모델.** SAP 판매문서 상태와 Salesforce Opportunity Stage는 개수도, 전이 규칙도, 시점도 다르다. "수주"가 SAP에선 오더 생성, SFDC에선 Closed Won인데 두 시점이 며칠 차이 난다. 컬럼명을 통일해도 **숫자는 계속 안 맞는다.**

**문제 3 — 지표 정의.** "매출"이 SAP는 청구 기준, Salesforce는 파이프라인 기준. 이건 딕셔너리가 아니라 **시맨틱 레이어**에서 풀어야 한다.

경험칙으로 이 셋이 전체 난이도의 80%이고 명명 규칙은 20%다. 순서를 반대로 잡는 조직이 대부분이다.

## 4. 잘하기 위한 여섯 가지

**① 범위를 프로세스로 자른다. 사전 전체로 자르지 않는다.**
전사 사전을 먼저 완성하려는 순간 실패 확률이 급등한다. 시스템 경계를 실제로 넘나드는 흐름 하나를 골라 그것만 완결한다. 이 조합이면 보통 Lead-to-Cash다. Salesforce 기회 → SAP 오더·청구 → OutSystems 포털 조회. 엔티티 5~10개, 필드 100~200개면 충분하다.

**② 표준을 강제할 지점을 "시스템 내부"가 아니라 "경계"로 옮긴다.**
가장 중요한 설계 결정이다. 각 시스템 내부는 각자의 관습대로 두고, **인터페이스 계약(API 스키마, 이벤트 페이로드, 통합 테이블)에만 캐노니컬 이름을 강제**한다.

- 검수 항목: "SAP 컬럼이 표준어인가" ❌
- 검수 항목: "이 API 페이로드의 모든 필드가 캐노니컬 용어에 매핑되어 있는가" ✅

이렇게 하면 SAP를 손대지 않고도 통제 대상에 넣을 수 있다.

**③ 매핑을 문서가 아니라 실행되는 코드로 관리한다.**
Excel 매핑표는 3개월 안에 죽는다. 매핑을 Git에 YAML/JSON으로 두고, CI에서 검증하고, 통합 미들웨어가 그걸 참조하게 한다. **"매핑에 없는 필드가 페이로드에 나타나면 빌드 실패"** 규칙 하나가 준수율 리포트 백 장보다 효과적이다.

**④ 각 시스템의 메타데이터를 자동으로 긁어온다.**
SAP는 DDIC/CDS 뷰 애노테이션, Salesforce는 Metadata API, OutSystems는 엔티티 모델과 LifeTime API. Salesforce는 연 3회 릴리스, SAP는 업그레이드, OutSystems는 상시 배포다. **수동 동기화 전제로 설계하면 반드시 무너진다.** "새 필드인데 매핑 없음"을 자동 탐지해 담당자에게 던지는 루프를 만들어야 한다.

**⑤ 소유권을 IT가 아니라 도메인에 둔다.**
`Customer`의 정의를 DA가 정하면 아무도 안 지킨다. 영업 도메인 오너가 정하고 그 사람 이름이 사전에 박혀 있어야 분쟁 시 결론이 난다. 예전 SI에서 승인 워크플로우가 병목이 된 건 **승인자가 업무를 몰랐기 때문**이다.

**⑥ LLM은 여기에 정확히 잘 맞는다.**
이 프로젝트의 최대 비용은 매핑 초안 작성이다. `KNA1`의 100여 개 필드가 각각 어떤 개념인지 사람이 읽는 데만 몇 주가 걸린다. LLM에 **필드명 + 타입 + 샘플값 + 기존 매핑 사례**를 주고 캐노니컬 후보를 제안하게 하면 초안 시간이 크게 줄어든다. 다만 2장에서 본 대로 모호한 필드에서 그럴듯한 오답을 내므로 반드시 **제안(LLM) / 승인(사람)** 구조로 가야 하고, 승인 이력이 남아야 한다. 자동 반영은 금물이다.

## 5. 어떻게 만들 것인가 — 파이프라인과 단일 HTML

주도자는 한 명이고, 개발자 대부분은 완성된 걸 조회하는 입장이라고 하자. **단일 HTML로 충분하다.** 오히려 이 상황에선 그게 정답에 가깝다. 읽는 사람이 100명이고 쓰는 사람이 1명이면 서버·계정·워크플로우는 전부 비용이고 아무도 안 쓴다.

다만 **HTML은 산출물이지 원본이 아니어야 한다.** 이 분리를 안 해두면 3개월 뒤 "HTML을 직접 고치는" 상태가 되고 그때부터 죽는다.

<pre class="mermaid">
flowchart LR
    S1["SAP DDIC/CDS"] --> R["raw/*.json · 원본 그대로"]
    S2["SFDC Metadata API"] --> R
    S3["OutSystems LifeTime"] --> R
    R --> P["physical.json · 필드/타입/샘플값 정규화"]
    P --> B["build.py · 검증 + 갭 계산 + JSON 임베드"]
    Y["canonical.yaml · 사람이 관리하는 유일한 원본"] --> B
    L["LLM 매핑 제안"] -.-> Y
    B --> H["dictionary.html · 단일 파일 배포"]
</pre>

파일 구조는 이 정도면 충분하다.

```
data-dictionary/
├─ raw/                  # 각 시스템에서 긁은 원본. 손대지 않음
│   ├─ sap_ddic.json
│   ├─ sfdc_metadata.json
│   └─ oss_entities.json
├─ physical.json         # 정규화 결과. 자동 생성
├─ canonical.yaml        # ★ 사람이 편집하는 유일한 파일
├─ build.py              # 검증 + HTML 생성
└─ dist/dictionary.html  # 배포물
```

`canonical.yaml`을 Git에 두면 변경 이력·리뷰·롤백이 공짜로 따라온다. **승인 워크플로우를 따로 만들 필요가 없다. PR이 곧 승인 절차다.**

### build.py가 반드시 막아야 할 것

빌드 실패로 막아야 실효가 생긴다.

- `canonical.yaml`의 매핑이 `physical.json`에 실재하는 필드인가 (오타·삭제된 필드 탐지)
- 한 물리 필드가 두 개념에 중복 매핑되지 않았는가
- `scope`에 있는데 매핑이 없는 항목 = **갭**으로 집계
- `physical.json`에 있는데 어느 개념에도 안 붙은 필드 = **미분류**로 집계
- 코드값 대응표에 정의되지 않은 값이 샘플에 등장하는가

### 1인 운영 워크플로 — 주 1회 30분

1. 수집 스크립트 실행 → `physical.json` 갱신
2. 빌드 → **신규/변경/삭제 필드 리스트**가 뜸
3. LLM에 (필드명 + 타입 + 샘플값 + 기존 매핑 사례)를 주고 매핑 후보 제안받기
4. 제안을 `status: proposed`로 커밋 → 도메인 담당자 확인 후 `confirmed`로 승격
5. 빌드 → HTML 재배포

3~4단계가 핵심이다. **LLM 제안과 사람 확정을 데이터에서 구분**해두면 보는 사람이 "이건 아직 검증 안 된 추정"인지 알 수 있다. 이걸 뭉뚱그리면 2장에서 말한 그럴듯한 오답이 확정 사실처럼 유통된다.

## 6. 프로토타입

말로만 하면 감이 안 오므로 실제로 만들어 붙였다.

**→ [전사 용어사전 프로토타입 열기](/demo/enterprise-dictionary.html)**

Lead-to-Cash 범위의 샘플 데이터 17개 개념이 들어 있다. 최상단 `DICT` 객체만 교체하면 그대로 쓸 수 있는 단일 파일이다. 실제 기업 데이터가 아니라 설계를 보여주기 위한 가짜 데이터다.

**기능**

- 개념 목록 · 도메인 필터 · 통합 검색 (`/`로 포커스, ↑↓ 이동)
- 개념 상세: 정의, 소유 도메인, 자료형, 적용 범위, 비고
- 시스템별 대응 필드 3-트랙 뷰 (SAP / Salesforce / OutSystems)
- 코드값 대응표, 사용 인터페이스 목록
- 역방향 조회 (물리 필드명 → 개념)
- 갭 리포트 (범위 내 미매핑 + 개념 미등록 물리 필드)
- 헤더의 시스템별 매핑 커버리지 게이지
- URL 해시 딥링크, 수정 요청 양식 클립보드 복사

**설계에서 의도적으로 넣은 것**

| 결정 | 이유 |
|---|---|
| 갭을 빗금 처리로 가장 눈에 띄게 | 사전의 실제 가치는 "채워진 칸"이 아니라 **"비어 있다는 사실을 아는 것"** |
| 범위 밖(해당 없음)과 갭을 분리 | `Opportunity.stage`가 SAP에 없는 건 정상, `Customer.creditLimit`이 SFDC에 없으면 문제. 안 나누면 갭 리포트가 노이즈로 가득 차 아무도 안 본다 |
| 확정 / 제안을 항목 단위로 표시 | LLM 제안이 확정 사실로 유통되는 걸 막는 최소 장치 |
| 검색 한 칸으로 양방향 | 개발자가 겪는 상황은 "코드에서 이상한 컬럼명을 만났다"이지 "개념명을 안다"가 아님 |
| 해결되지 않는 걸 명시 | 매핑표로 안 풀리는 문제(지표 정의, 시점 차이, ID 대응)가 있다는 걸 사전 안에서 드러내야 잘못 신뢰하지 않는다 |

**샘플 데이터에 일부러 심어둔 함정 사례**

- `Customer.status` — SAP에 휴면(DORMANT) 개념이 없어 대응 코드가 비어 있음
- `Customer.taxId` — 세 시스템의 하이픈 포함 여부가 제각각
- `Customer.owner` — SAP는 파트너기능 기반이라 1:1 매핑이 성립하지 않음
- `Order.date` — SFDC의 CloseDate는 엄밀히 수주일이 아님 (제안 상태)
- `Revenue.net` — 재무(청구 기준)와 영업(Closed Won 기준)의 정의 충돌
- `Product.sku` — SAP는 선행 0 채움, SFDC는 미보존 → 조인 시 정규화 필수

이 여섯 개가 사실상 이 사전의 존재 이유다. 이름이 같아도 안 맞는 것들이 어디인지 드러내는 것.

## 7. 지표와 궤도이탈 신호

### 준수율은 지표가 아니다

| 지표 | 정의 |
|---|---|
| **매핑 커버리지** | 인터페이스 페이로드 필드 중 캐노니컬에 매핑된 비율 |
| **미매핑 신규 필드 수** | 각 시스템 릴리스 후 잡히는 건수와 처리 리드타임 |
| **정합성 불일치 건수** | 세 시스템 간 대사(reconciliation) 오차 |
| **지표 일치율** | 같은 질문에 SAP 리포트 / SFDC 대시보드 / 포털 화면이 같은 숫자를 내는가 |

마지막 지표가 사실상 이 프로젝트의 존재 이유다. 여기가 안 맞으면 사전이 아무리 잘 만들어져도 성공이 아니다.

### 이 신호가 보이면 궤도를 벗어난 것

- SAP 표준 필드 이름을 바꾸자는 논의가 진행 중
- 산출물이 대부분 "표준단어 목록"이고 매핑표는 얇음
- 캐노니컬 모델이 너무 추상적이라 세 시스템 어디에도 안 맞음 (`Party`, `Item`, `Event`만 있는 모델)
- 매핑이 Excel에 있고 갱신 담당이 정해져 있지 않음
- 크로스레퍼런스(ID 매핑) 설계가 아직 없음
- 준수율 %를 KPI로 잡고 있음

## 시작 권고

`Customer` 5개 + `Order` 5개 정도로 먼저 한 바퀴 돌려보길 권한다. 17개 항목을 채우는 것보다, **수집 → 매핑 → 빌드 → 배포 루프가 실제로 도는지** 확인하는 게 먼저다.

한 줄 요약. 전통 SI 표준사전은 통제 가능한 DB를 전제로 명명을 강제했고, 강제 장치가 사라지는 운영 단계에서 무너졌다. LLM 시대에 메타데이터는 대체되는 게 아니라 LLM의 필수 입력이 되었고, 그래서 방치의 대가가 즉시 드러나게 됐다. SaaS 혼재 환경에서는 명명을 통제할 수 없으므로 목표를 **"같은 이름"에서 "같은 의미로의 번역"**으로 재정의하고, 산출물을 매핑 자산으로 만들고, 강제 지점을 인터페이스 경계로 옮겨야 한다.
