앞선 [LLM Wiki 글](/2026/08/03/llm-wiki-pattern/)에서 "이해를 쿼리 타임이 아니라 빌드 타임에 한다"는 패턴을 정리했다. 그런데 이걸 실제 서비스에 얹으려면 도메인마다 답이 달라진다.

이번 글은 그중 가장 요청이 많은 케이스 하나를 끝까지 판단해본다. **제품·장비·사내 업무 매뉴얼을 AI가 답해주는 서비스**를 만든다고 할 때, RAG로 갈 것인가 LLM Wiki로 갈 것인가.

---

## 결론부터

**RAG를 뼈대로 하고, LLM Wiki는 "지도"로만 얹어라. 절차와 수치는 절대 위키에서 답하지 마라.**

- 매뉴얼은 **원문 자체가 정답**인 도메인이다. LLM Wiki의 핵심 동작인 합성(synthesis)이 여기서는 **기능이 아니라 리스크**다.
- 대신 매뉴얼은 다중 홉 질문(오류코드 → 조치절차 → 부품 → 안전주의)이 많고, 같은 질문이 수천 번 반복된다. 이건 LLM Wiki가 강한 지점이다.
- 그래서 **위키는 경로를 찾는 데만 쓰고, 최종 답변의 수치·절차는 원문에서 그대로 인용**하는 3층 구조가 맞다.
- 토큰 비용은 **RAG < 하이브리드 < 위키** 순서가 뒤집히지 않는다. 위키가 싸지는 구간은 없다. 다만 그 차액은 오답 처리 비용의 30분의 1이라 **결정 변수가 아니다**.
- "LLM Wiki = RAG의 상위 호환"이라고 보고 갈아타면 매뉴얼 도메인에서는 손해다.

## 1. 매뉴얼 도메인의 특수성

일반 문서 Q&A와 다른 점이 다섯 가지 있고, 이게 모든 판단의 전제다.

| # | 특성 | 함의 |
|---|---|---|
| 1 | **원문 충실성이 법적·안전 요건** | "3.5 N·m로 조이시오"가 "적정 토크로 조이시오"가 되면 사고 + 책임 |
| 2 | **버전이 폭증한다** | 제품 라인 × 모델 × 펌웨어 × 언어 = 조합이 수십~수백 |
| 3 | **질문 반복도가 극단적으로 높다** | 상위 100개 질문이 전체 트래픽의 60~80%를 먹는 게 보통 |
| 4 | **오답이 곧 클레임·리콜** | 사전 검수 가능 여부가 규제 산업에서 결정적 |
| 5 | **원본이 이미 구조화되어 있다** | 매뉴얼은 이미 목차·섹션·상호참조를 가진 준(準) 위키 |

5번을 특히 주목할 만하다. **코드베이스에서 LLM Wiki가 큰 이득을 보는 이유는 코드에 설명이 없기 때문**이다. 사람이 읽을 수 있는 구조를 LLM이 새로 만들어주니 가치가 크다.

매뉴얼은 다르다. 이미 사람이 목차를 잡고 챕터를 나누고 "3.2절 참조"까지 달아놨다. 위키로 재컴파일해서 얻는 증분 이득이 코드베이스보다 훨씬 작다. 출발점부터 조건이 다르다.

## 2. 축별 비교

| 축 | RAG | LLM Wiki | 매뉴얼 판정 |
|---|---|---|---|
| **원문 충실성** | 청크를 그대로 넘김 → 원문 보존 | 합성 → 뉘앙스·수치 변형 위험 | **RAG 필수** |
| **답변 일관성** | 검색이 흔들리면 답도 흔들림 | 같은 문서 → 같은 답 | Wiki 우세 |
| **사전 검수 가능성** | 런타임 생성이라 불가 | 정적 산출물 → 사람이 미리 검수·승인 | **Wiki 결정적 우세** |
| **다중 홉 질문** | 반복 검색, 자주 실패 | 링크를 타고 이동 → 강함 | Wiki 우세 |
| **버전·모델 분기** | 메타데이터 필터 한 줄 | 버전마다 재컴파일 → N배 | **RAG 압승** |
| **다국어** | 다국어 임베딩으로 흡수 | 언어별 컴파일 또는 번역 레이어 | **RAG 우세** |
| **개정판 반영** | 재색인만 (분 단위, 저렴) | 재컴파일 (시간 단위, 비쌈) | **RAG 압승** |
| **초기 구축 비용** | 낮음 | 높음 (전체 1회 컴파일) | RAG 우세 |
| **쿼리당 비용** | 단발 호출 → 확실히 저렴 | 에이전틱 루프 → 항상 같거나 비쌈 | **RAG 우세** |
| **"모른다" 판별** | 청크가 없으면 헛소리 위험 | 문서 부재를 명시적으로 인지 | Wiki 우세 |
| **이미지·도해 연결** | 청크와 그림이 분리되기 쉬움 | 문서 단위라 그림 맥락 유지 | Wiki 우세 |

### 쿼리당 비용: LLM Wiki가 싸지는 지점은 없다

지난 글에서 "LLM Wiki는 쿼리당 비용이 RAG보다 낮다"고 썼는데, **이건 정정해야 한다.** 매뉴얼 도메인에서 토큰만 놓고 보면 위키가 RAG보다 싼 구간은 없다.

구조가 다르기 때문이다.

- **RAG**: 검색 1회 → 생성 1회. **단발 호출**이다.
- **위키 탐색**: 목차 읽고 → 문서 열고 → 링크 타고. **에이전틱 루프**고, 루프는 매 턴 이전 컨텍스트를 다시 실어 보낸다.

프롬프트 캐싱이 격차를 줄여준다. 캐시 읽기는 입력가의 약 10%다. 그리고 캐싱은 **위키 쪽에 더 유리하게 작동한다** — 위키 탐색은 `시스템 프롬프트 + 목차 + 이미 읽은 문서`라는 긴 안정적 프리픽스를 갖는 반면, RAG가 실어 보내는 청크는 질문마다 통째로 바뀌어 캐시할 게 없다. 그래도 역전까지는 안 간다.

질문 1건당 입력 토큰 (등가 = 캐시 읽기를 0.1배로 환산한 값):

| 질문 유형 | 방식 | 단순 누적 | 캐시 적용 등가 |
|---|---|---|---|
| 단순 조회 | RAG 단발 | 6K | **4K** |
| 단순 조회 | Wiki 탐색 (2턴) | 13K | 6K |
| 다중 홉 | RAG 단발 | 6K | **4K** (단, 자주 오답) |
| 다중 홉 | RAG 에이전틱 (3회 검색) | 31K | 15K |
| 다중 홉 | Wiki 탐색 (3턴) | 28K | 15K |

읽는 법이 두 가지다.

**단순 질문에서는 RAG가 1.5배 싸다.** 위키 탐색은 목차를 한 번 더 읽는 만큼 더 쓴다.

**다중 홉에서는 에이전틱 RAG와 위키가 사실상 동률이다.** 둘 다 에이전틱 루프라 토큰 구조가 같기 때문이다. 여기서 갈리는 건 비용이 아니라 **정확도**다 — 같은 토큰을 쓰고 위키는 링크를 따라가 맞는 답을 내고, RAG는 유사도 검색으로 조각을 긁어모으다 실패한다.

그래서 하이브리드의 논리는 "유형별로 싼 쪽을 고른다"가 아니다. **트래픽의 75%를 차지하는 단순 질문을 싼 경로로 흘려보내고, 비싼 경로는 그게 필요한 25%에만 쓴다**는 것이다.

## 3. 질문 유형별 판정

실제 매뉴얼 서비스 트래픽을 유형으로 쪼개면 이렇게 갈린다.

| 질문 유형 | 예시 | 적합 |
|---|---|---|
| 단순 사실 조회 | "정격 전압이 몇 V?" | RAG |
| 절차 조회 | "필터 교체 순서" | RAG (원문 그대로) |
| 오류코드 → 조치 | "E-047 조치 방법" | **Wiki** (코드표→절차→부품→안전) |
| 조건부 분기 | "A 모델인데 B 옵션이 달렸을 때" | **Wiki** |
| 개념 이해 | "이 장비 냉각 방식이 왜 이렇게 설계됐나" | **Wiki** |
| 모델 간 비교 | "X100과 X200 차이" | **Wiki** (문서 간 교차) |
| 실시간 상태 | "지금 재고 / 현재 펌웨어 버전" | 둘 다 아님 → API |

여기서 실무적 결론이 나온다. **트래픽의 대부분(단순 조회·절차)은 RAG로 충분하고, 위키가 필요한 건 소수의 어려운 질문이다.** 전체 매뉴얼을 위키화하는 건 낭비다.

## 4. 권장 아키텍처: 3층 하이브리드

<pre class="mermaid">
flowchart TB
    Q[사용자 질문] --> RT{질문 유형 라우팅}
    RT -- 단순 조회·절차 --> L0
    RT -- 다중 홉·비교·개념 --> L1
    L1["L1. 위키 레이어 : 오류코드 인덱스, 절차 상호참조 맵, 개념 문서 — 라우팅 전용, 근거 아님"]
    L0["L0. 원문 저장소 (불변) : 매뉴얼 원문 청크 + 임베딩 + 메타데이터(모델·버전·언어·페이지)"]
    L1 -- 어느 원문을 볼지 지시 --> L0
    L0 --> L2
    L2["L2. 답변 합성 : 수치·절차는 원문 verbatim 인용, 맥락 설명만 위키 활용, 출처 표기 필수"]
    L2 --> OUT["답변 + [매뉴얼명 v버전, p.페이지]"]
</pre>

핵심 규칙 세 가지다.

### ① 위키는 근거가 될 수 없다

위키 문서의 역할은 "어느 원문을 봐야 하는지" 알려주는 데서 끝난다. 최종 답변의 모든 수치·절차·경고문은 L0 원문에서 그대로 가져온다.

위키 문장을 인용해 답하는 순간, 지난 글에서 다룬 **지식 오염(knowledge poisoning)이 서비스 답변에 직접 실린다.** 요약의 요약이 고객에게 나가는 구조가 되는 것이다. 내부 문서라면 나중에 고칠 수 있지만, 매뉴얼 서비스에서는 이미 나간 답변이다.

### ② 위키는 전체가 아니라 상위 질문에만 만든다

질의 로그에서 다중 홉·반복 질문을 뽑아 그 영역만 위키화한다. 전체 매뉴얼 위키화는 버전이 늘어나는 순간 유지가 불가능해진다.

### ③ 버전은 위키가 아니라 메타데이터로 가른다

위키는 "모델 공통 개념·오류코드 체계"처럼 버전 간 안정적인 층에만 둔다. 버전별로 달라지는 수치는 L0 메타데이터 필터로 처리한다.

이걸 어기면 모델 30종 × 언어 5개 = **위키 150개**를 관리하게 된다. 개정판이 하나 나올 때마다 어느 위키를 다시 컴파일해야 하는지도 추적이 안 된다.

## 5. 비용 감각 — 그리고 왜 이게 결정 변수가 아닌가

전제: 매뉴얼 500페이지(약 250K 토큰), 모델 10종, 월 질의 50,000건, 단순 75% / 다중 홉 25%. 모델은 Sonnet 5 정가($3 / $15 per MTok) 기준. 순수 RAG는 다중 홉에서 틀린 만큼 재질의가 붙어 실제 처리량이 55,000건이 된다고 봤다.

| 항목 | 순수 RAG | 하이브리드 | 순수 LLM Wiki |
|---|---|---|---|
| 초기 구축 | 임베딩만, 무시 가능 | 상위 20%만 컴파일 | 전체 컴파일 × 모델 수 |
| 개정판 반영 | 재색인 (분 단위) | 위키 해당분만 재컴파일 | 전체 재컴파일 (시간 단위) |
| **월 추론 비용** | **~$1,020** | **~$1,410** (1.4배) | **~$1,730** (1.7배) |
| 다중 홉 정확도 | 낮음 (재질의·오답) | 높음 | 높음 |
| 사전 검수 | 불가 | 어려운 질문만 가능 | 가능 |

**순서가 뒤집히지 않는다.** RAG가 제일 싸고, 위키가 제일 비싸고, 하이브리드가 그 사이다. 하이브리드는 "더 싼 구조"가 아니라 **비싼 경로의 적용 범위를 25%로 묶어둔 구조**다.

### 그런데 이 표는 결정에 쓰면 안 된다

여기까지 계산하고 나면 오히려 반대 결론이 나온다. **추론 비용은 이 결정의 지배 변수가 아니다.**

순수 RAG가 다중 홉 12,500건 중 40%를 틀린다고 하자. 오답 5,000건이다. 그중 절반만 상담원 연결로 넘어가고 1건 처리 비용을 $5로 잡으면 **월 $12,500**이다.

두 아키텍처의 추론 비용 차액은 $390이다. **32배 차이다.**

| | 월 비용 |
|---|---|
| 아키텍처 간 추론 비용 차액 | ~$390 |
| 오답으로 발생하는 상담 비용 | ~$12,500 |

즉 토큰 비용으로 아키텍처를 고르는 건 자릿수를 잘못 보는 것이다. 하이브리드를 쓰는 근거는 "싸다"가 아니라 **"토큰을 1.4배 더 써서 30배 비싼 실패를 막는다"**이다.

반대로 이 계산은 **위키를 전면 도입하지 말아야 할 이유**도 설명한다. 단순 조회 75%는 RAG로도 이미 정확하다. 거기에 위키 경로를 태우면 정확도 개선 없이 토큰만 1.5배 더 쓴다. 순수 위키가 하이브리드보다 비싼 이유가 정확히 이것이다.

## 6. 도입 순서

| 단계 | 기간 | 내용 |
|---|---|---|
| 1 | ~1개월 | **순수 RAG로 출시.** 페이지·버전 메타데이터를 처음부터 정확히 심는다 |
| 2 | 2~3개월 | 질의 로그 수집. 재질의율·무응답률 높은 질문을 클러스터링 |
| 3 | +1개월 | 상위 클러스터만 위키 컴파일. 오류코드 인덱스부터 시작 |
| 4 | 상시 | 위키는 사람 검수 후 승인 배포, RAG는 자동 재색인 |

1단계에서 메타데이터를 대충 심으면 나중에 못 붙인다. PDF에서 페이지 번호와 모델 코드를 추출하는 건 색인 시점에만 쉽고, 청크가 된 뒤에는 복원이 어렵다.

2단계를 건너뛰고 처음부터 위키를 만들려는 유혹이 크다. 그런데 **어떤 질문이 다중 홉인지는 로그를 봐야만 안다.** 추측으로 만든 위키는 대부분 안 읽힌다. "당연히 이게 어려울 것"이라고 생각한 항목과 실제 재질의가 몰리는 항목은 거의 겹치지 않는다.

---

## 7. 반드시 막아야 할 것

매뉴얼 서비스에서 사고로 이어지는 실패 모드는 정해져 있다. 파이프라인에 강제 규칙으로 박아두자.

- **수치 합성 금지** — 토크값, 전압, 온도, 시간, 약품 농도는 원문 문자열 그대로. 린트로 강제한다(답변 내 `숫자+단위` 패턴이 인용된 원문에 존재하지 않으면 출력 차단)
- **안전 경고문 누락 금지** — 요약에서 가장 잘 날아가는 게 "⚠ 주의" 블록이다. 절차 답변에는 해당 절의 원문 경고문 전체를 그대로 끌고 온다
- **버전 혼선 금지** — 답변에 모델·버전이 표기되지 않으면 출력하지 않는다. 사용자가 모델을 안 밝혔으면 먼저 되묻는다
- **모르는 걸 답하기 금지** — 원문에 없으면 "매뉴얼에 해당 내용 없음 + 담당자 연결"로 종료한다. 매뉴얼 서비스에서 그럴듯한 추측은 최악의 실패다

마지막 항목이 실제로는 가장 어렵다. LLM은 빈칸을 메우려는 성향이 강해서, 프롬프트에서 **"모른다고 답하는 것이 정답인 경우가 있다"고 명시적으로 허가**해야 겨우 동작한다.

---

## 정리

- 매뉴얼은 **원문이 권위를 갖는 도메인**이다. 합성이 기본 동작인 LLM Wiki를 그대로 얹으면 안 된다.
- 그렇다고 RAG만으로는 오류코드 조치나 조건부 분기 같은 다중 홉 질문을 못 푼다.
- 답은 **위키를 라우팅·개요 층으로 한정하고 근거는 원문에 두는 3층 구조**다.
- 순서는 RAG 먼저, 로그 분석 다음, 위키는 마지막이다. 반대로 하면 안 읽히는 위키를 비싸게 만들고 유지하게 된다.
- **토큰 비용으로 아키텍처를 고르지 마라.** RAG가 싼 건 맞지만, 그 차액은 오답 하나가 만드는 상담 비용 옆에서 자릿수가 다르다.
- 위키를 얹어서 얻는 진짜 이득은 정확도만이 아니라 **사전 검수 가능성**이다. 규제 산업이라면 이쪽이 더 큰 이유가 된다.
