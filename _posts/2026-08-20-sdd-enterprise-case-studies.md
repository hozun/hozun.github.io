[SDD 확산 글](/2026/07/22/sdd-diffusion-spec-as-contract.html)에서 "스펙이 계약이 된다"고 썼고, [산출물 글](/2026/07/22/sdd-lowcode-spec-to-build.html)에서는 스펙·태스크를 실제 형태로 보여줬다. 두 글 모두 방법론 쪽이었다. 이번엔 **실제로 도입한 조직에서 무슨 일이 일어났는지**만 모았다. 성공과 실패 양쪽 다.

결론부터.

- SDD는 2026년 4월 Thoughtworks 기술 레이더 34호 기준 여전히 **Assess(탐색) 링**이다. Adopt도 Trial도 아니다.
- 성공 근거가 탄탄한 영역은 **경계가 명확하고 계약이 기계 검증 가능한 곳**(API 스키마, 상태 기계, 안전 필수 제어 로직)에 몰려 있다.
- 실패 패턴은 거의 하나로 수렴한다. **브라운필드에서 전체를 스펙화하려는 시도.**
- 돌아다니는 "생산성 N% 향상" 숫자는 대부분 1차 출처가 없다.

---

## 전제: 지금 SDD는 어디쯤 와 있나

레이더 34호는 이번 사이클에서 두 진영이 갈리는 중이라고 관찰했다.

- 최소한의 구조만 두고 코딩 에이전트의 향상되는 역량에 기대는 팀
- 정형화된 워크플로와 상세 명세를 선호하는 팀

Thoughtworks 팀들은 주로 **브라운필드 환경**에서 GitHub Spec Kit으로 실험 중이라고 밝혔다. 눈여겨볼 건 34호에서 기법으로서의 "spec-driven development" 자체가 레이더에서 빠지고, 대신 이를 구현하는 도구들(Spec Kit, OpenSpec)이 Assess에 올랐다는 점이다. 레이더는 이를 용어가 안정화되기 전에 빠르게 확산되는 **의미 확산(semantic diffusion)** 사례로 언급했다.

즉 "검증된 성공 방법론"이 아니라 아직 실험 단계라는 전제로 읽어야 한다.

## 1. 성공 사례

### 카카오페이 AI 플랫폼팀 (국내, 2026.3 공개)

가장 구체적으로 공개된 국내 엔터프라이즈 사례다.

**배경.** 에이전틱 코딩으로 개발 기간은 크게 단축했지만, 프로젝트가 고도화될수록 무분별한 코드 생성과 환각이 문제가 됐다. 후반으로 갈수록 AI가 생성한 코드를 검토·수정하는 시간이 점점 길어졌고, 그래서 spec-kit을 도입했다.

**워크플로.**

<pre class="mermaid">
flowchart LR
    C[constitution] --> S[specify]
    S --> CL[clarify]
    CL -.->|재정의| S
    CL --> P[plan]
    P --> T[tasks]
    T --> A[analyze]
    A --> I[implement]
</pre>

원칙 하나가 핵심이다. **각 단계에서 마음에 안 드는 부분이 있어도 산출물을 직접 고치지 않고 `specify`로 돌아가 스펙을 재정의한다.** 직접 수정하면 스펙 문서와 실제 코드·계획이 불일치해 일관성 유지 원칙에 어긋나고, 나중에 스펙 문서를 보는 개발자가 혼란스러워지기 때문이다.

**얻은 것.**

| 항목 | 내용 |
|---|---|
| 코드 일관성 | tasks 단계에서 구체적 작업 지시가 내려와 일관성 상승. 기존 바이브 코딩은 대화가 길어질수록 AI가 이전 코드 패턴을 기억하지 못해 스타일이 제각각이 됨 |
| 거버넌스 | 보안·테스팅처럼 일관성이 중요한 요소를 constitution에 명시하고, tasks에 반영 여부를 즉시 확인·추가 가능 |
| 기획 협업 | `clarify` 명령이 기획 문서·요구사항에서 놓친 점을 찾아줌. 개발자뿐 아니라 기획자와 함께 보기에 유용 |
| 지식 공유 | 협업 환경에서 다른 개발자가 어떤 작업을 했는지 스펙 문서로 명확히 파악 |

같은 팀이 밝힌 단점은 뒤 실패 섹션에 따로 정리했다.

---

### 금융 마이크로서비스 API-First — 변경 사이클 타임 75% 감소

arXiv 2602.00180의 사례연구 1이다.

**문제.** "통합 지옥(integration hell)". 마이크로서비스들이 함께 배포되면 자주 실패했다. 팀마다 API 계약에 대해 서로 호환되지 않는 가정을 세웠고, 그 불일치는 통합 테스트 단계에서야 드러나 비싼 재작업을 유발했다.

**해법 구조.**

1. 어떤 서비스든 구현 전에 OpenAPI 명세를 작성 (엔드포인트, 요청/응답 스키마, 에러 조건)
2. 소비자 팀이 코딩 시작 전에 그 명세를 리뷰하고 피드백 → 통합 논의를 앞당김
3. Specmatic으로 명세에서 목(mock) 서버 생성 → 프론트엔드가 백엔드와 병렬 진행
4. CI에서 구현 서비스가 명세와 일치하는지 검증 → 어긋나면 빌드 실패

**핵심.** 호환성 문제가 프로덕션이 아니라 **스펙 리뷰 단계**에서 잡혔다. 명세가 모든 당사자가 신뢰하는 계약이 되면서 재작업의 원인이던 모호성이 제거됐다.

다만 이건 SDD의 승리라기보다 **"design-first / API-first"가 수년간 표준 관행이었다**는 사실의 재확인에 가깝다. SDD 중 성공 근거가 가장 탄탄한 영역이 하필 가장 오래된 영역이라는 점은 그 자체로 시사적이다.

---

### 자동차 ECU 개발 — Model-Based (사례연구 3)

가장 극단적인 spec-as-source 형태이자, 20년 전부터 검증돼 온 사례다.

- 제어 알고리즘을 Simulink 블록 다이어그램과 상태 기계로 모델링 → **모델이 곧 명세**
- 코드가 존재하기 전에 모델 수준 시뮬레이션으로 알고리즘 오류를 잡음
- 검증 후 인증된 코드 생성기로 C 코드를 자동 생성
- 엔지니어는 생성 코드를 **절대 편집하지 않음.** 로직 변경이 필요하면 모델을 고치고 재생성

ISO 26262 안전 인증이 요구하는 "모든 코드 라인의 요구사항 추적성"이 구조적으로 확보된다. 수작업 코딩이었다면 노동집약적이었을 부분이다.

전제 조건이 명확하다. **생성기가 인증 수준으로 신뢰 가능할 때만** 성립한다.

---

### 엔터프라이즈 기능 개발 — BDD (사례연구 2)

**문제.** 개발자와 PM이 "done"의 의미를 두고 계속 충돌. 개발자가 요구사항을 충족했다고 믿고 구현하면 QA가 제품 기대와 다르다고 지적하고, 누구 해석이 맞는지 논쟁이 벌어졌다.

**해법.**

- PM이 Gherkin 시나리오로 기대 동작을 평문으로 작성
- 개발자가 step definition을 구현해 시나리오를 실행 가능한 테스트로 자동화
- **모든 시나리오가 통과해야 done** — 객관적이고 검증 가능한 완료 정의

분쟁이 생기면 시나리오가 권위를 갖는다. 시나리오가 틀렸으면 이해관계자 합의 하에 갱신하고, 코드가 틀렸으면 개발자가 고친다.

---

### GitHub GraphQL 스키마 — living contract 패턴

공개 GraphQL 스키마가 제품과 엔지니어링 사이의 살아있는 계약으로 기능하는 사례다. 강타입이고 introspection 가능하며, 버전 관리되고 공표된 breaking-change 정책으로 거버넌스된다.

- PM과 엔지니어가 스키마 제안을 함께 다듬고, 그 제안이 곧 문서 역할
- 코드 생성으로 강타입 클라이언트와 테스트가 나오므로, 한 번의 수정이 문서·SDK·검사를 동시에 갱신
- 스키마가 실행 가능하고 diff 가능하며 감사 가능한 단일 진리의 원천

## 2. 실패와 한계

### 브라운필드에서 무너진다 — 가장 일관된 패턴

Martinelli의 분석이 가장 신랄하다. Kiro, GitHub Spec Kit, BMad Method 세 도구가 공유하는 **암묵적 전제** 두 가지를 지적한다.

1. **백지에서 시작한다.** 워크플로가 "원하는 걸 설명하면 생성한다"에 최적화돼 있다. 500개 테이블짜리 Oracle 스키마, 확립된 아키텍처 패턴, 15년간 누적된 비즈니스 룰을 전혀 고려하지 않는다.
2. **개발자 한 명이 프로세스를 주도한다.** 엔터프라이즈 개발에 필수인 다중 이해관계자, 교차팀 의존성, 리뷰 프로세스, 컴플라이언스 요건을 상정하지 않는다.

엔터프라이즈 준비성을 표방하지만 **대규모 브라운필드 도입의 실증 근거는 얇다.** Amazon 자체 제품팀도 이 격차를 인정했고, Broadcom의 한 엔지니어는 "대부분의 개발자는 그린필드 아이디어에서 시작하지 않는다"고 표현했다.

BMad의 경우 Node.js 22+ 요구, 가파른 학습 곡선, 에이전트 오케스트레이션 오버헤드가 지적됐다. v6가 여전히 알파인데 신규 프로젝트에 권장된다는 점 자체가 성숙도를 말해준다.

### 규모의 벽 — 컨텍스트 한도 vs 리뷰 한도

InfoQ 분석의 결론은 직설적이다.

> 대형 기존 애플리케이션에서 전체 명세를 생성하면 **컨텍스트 한도를 넘기거나, 아니면 리뷰가 불가능할 만큼 거대한 명세가 나온다.**

10만 개 이상 파일 규모의 엔터프라이즈 코드베이스는 인간의 리뷰 역량과 검색 한계를 초과하지 않고서는 포괄적으로 명세화할 수 없다.

여기에 지식 손실 문제가 겹친다. 아키텍처 결정 기록(ADR)이 없고 테스트 커버리지도 거의 없는 상태에서는 점진적 기능 개발에 안전망이 아예 없다. 아키텍처 의도를 이해하던 엔지니어는 이미 퇴사했고, 현대 엔지니어는 레거시 기술을 배운 적이 없다.

**완화책은 전체 스펙화를 포기하는 것이다.**

| 단계 | 내용 |
|---|---|
| 1 | 새 스펙을 쓰기 전에 **기존 동작을 먼저 복원.** UI 요소, 바이너리, 데이터 계보 등 가시적 산출물에서 시작해 점진적으로 보강하고 원본까지 추적성 유지 |
| 2 | 시스템 전체가 아니라 **변경 영역만** 스펙화. "스펙은 변경 지점에 가장 가까운 곳에서 가장 상세해야 한다" |
| 3 | 버그 수정·기능 추가·리팩토링 각각을 해당 코드에 스펙을 덧붙일 기회로 활용 |

OpenSpec이 브라운필드에서 상대적으로 나은 평가를 받는 이유도 여기 있다. 완전한 명세를 미리 정의하는 대신 **스펙 델타**에 집중하고, propose → apply → archive 3단계로 가볍다.

### 과잉 명세의 부조리

Birgitta Böckeler(Thoughtworks)가 Kiro·spec-kit·Tessl을 직접 써본 기록에서 가장 많이 인용되는 대목.

> 작은 버그 하나를 고치는 데 요구사항 문서가 **사용자 스토리 4개, 수용 기준 총 16개**로 불어남. 거기엔 "개발자로서, 새로운 카테고리 형식이 도입될 때 시스템이 견고하게 유지되도록 변환 함수가 예외 상황을 우아하게 처리하기를 원한다" 같은 내용이 포함됨.

spec-kit에 대해서도 "어느 규모의 문제에 적합한지 확신이 서지 않는다"고 했다. 공개된 튜토리얼은 대개 처음부터 앱을 만드는 것에 기반해 있는데, 그건 **튜토리얼을 만들기 가장 쉬운 방식일 뿐**이다. 실제로 시도한 것 중 하나는 기존 대시보드 데이터를 요약하는 모달 기능(과거 팀 기준 3~5포인트 스토리)이었고, 결론은 **세 도구 중 둘은 기존 코드베이스에 도입할 경우 훨씬 더 많은 작업이 필요해 보였다**는 것이었다.

### 성공 사례 팀이 직접 밝힌 단점

카카오페이가 같은 글에서 명시한 내용이다. 성공 사례로 분류한 팀의 자기 평가라 더 참고할 만하다.

- **단계가 많아서** 처음 접하는 개발자에게 복잡하게 느껴짐
- **간단한 개발은 애매함.** specify를 수정할지 그냥 agent 모드로 처리할지 판단이 개발자마다 갈림
- **문서 폭발.** 파이프라인을 한 번 거치면 개발 문서가 굉장히 많이 생성되고 **토큰 소모도 큼** (문서 자체는 장점이 될 수도 있으나)
- **AI가 constitution을 무시할 때가 있음.** 코드 생성 시 tasks에 더 무게를 두는 것처럼 느껴져, constitution 기반으로 tasks가 잘 생성됐는지 다시 확인해야 함
- **specify 수정만으로 해결 안 되는 경우.** spec에 Figma MCP를 정의해뒀는데 tasks에서 누락돼, 결국 tasks.md를 직접 참조시켜 프롬프팅해야 했음

### 근본적 회의론

**Isoform — "현실이 스펙보다 빠르게 변한다."**

> 1990년대에는 긴 기능 명세서를 쓰고 코딩했다. 2010년경 애자일이 "모든 것을 미리 정의한다"는 발상을 대체했다. 지금 AI 코딩이 품질에서 고전하자 옛 플레이북이 돌아오고 있다.

상세한 스펙은 통제감을 주고 모든 케이스를 커버했다는 확신을 주지만, 그 확신은 대개 거짓이라는 지적이다. 소프트웨어 개발은 탐색적이고, 가장 중요한 통찰은 만들기 시작한 뒤에 나온다.

**Brandon Kindred — "Same Patterns, New Hype."** SDD는 대체로 워터폴/계약 설계의 리브랜딩이며, **가치는 도구가 아니라 스펙을 쓰면서 하는 사고에 있다**는 주장.

**Bryan Finster** — "SDD는 혁명이 아니다. 브랜딩을 입힌 BDD일 뿐이다." 다만 그 브랜딩에도 목적은 있다는 반론이 따라붙는다. 스펙이 참고용이 아니라 권위를 가져야 하며, 현대 도구가 예전엔 인간의 규율에 맡겨졌던 것을 강제할 수 있음을 상기시킨다는 점이다.

**Thoughtworks의 공식 입장**은 실행 가능한 코드가 여전히 유지보수를 요하는 진리의 원천이라며, **"스펙만으로 충분하다"는 관점을 명시적으로 거부**한다.

---

### 문헌이 정리한 공통 실패 모드

| 실패 모드 | 증상 | 대응 |
|---|---|---|
| **과잉 명세** | 스펙이 의사코드가 됨. 프로그램을 두 번 쓴 셈 | 모호성 제거에 필요한 최소 수준만 |
| **스펙 부패** | 코드가 바뀌어도 스펙이 안 따라감. 문서 가치 상실, 신뢰 붕괴 | 스펙-코드 괴리 시 실패하는 자동 테스트로 강제 |
| **관료화** | 스펙이 명료화 도구가 아니라 채워야 할 양식이 됨 → 팀이 편법 쓰거나 포기 | 오버헤드 대비 이해도·품질 개선 여부로 판단 |
| **도구 복잡도** | 생성된 계획·태스크·중간 문서에 팀이 익사 | 단순하게 시작, 효과가 입증될 때만 복잡도 추가 |
| **거짓 확신** | 스펙 테스트 통과 ≠ 올바른 소프트웨어. **스펙이 틀렸으면 코드는 틀린 것을 충실히 구현** | 스펙도 코드와 동일한 수준의 리뷰 대상 |
| **목발로서의 스펙** | 개발자가 스펙의 서비스 경계 설명을 구현 확인 없이 신뢰 → 문서를 현실의 대리물로 취급한 워터폴의 실수 반복 | AI가 코드베이스 분석으로 생성한 스펙은 "평균적으로 정확하지만 특정 지점에서 틀릴" 수 있음을 전제 |

**스테일 스펙이 스테일 설계 문서보다 위험한 이유:** 낡은 설계 문서는 그걸 읽는 다음 엔지니어 한 명을 오도한다. 낡은 스펙은 **더 나은 판단을 할 수 없는 에이전트들**을 오도하고, 그들은 현실과 맞지 않는 계획을 자신 있게 실행한다.

## 3. 패턴 정리

### 성공이 나오는 조건

- **경계가 명확하고 계약이 기계 검증 가능한 영역** — API 스키마, 상태 기계, 안전 필수 제어 로직
- **팀 간 조율 비용이 원래 컸던 지점** — 병렬 개발 블로커, 통합 실패, "done" 정의 분쟁
- **장수하고 유지보수자가 여럿인 시스템** — 스펙이 인력 교체를 견디는 문서 역할
- **규제 도메인** — 요구사항→구현 추적성이 어차피 의무
- **레거시 현대화** — 기존 동작을 스펙으로 추출해두면 재구현 시 기능 보존을 검증 가능
- **생성 도구가 성숙하고 신뢰 가능한 경우에만 spec-as-source** (Simulink/OpenAPI 수준)

### 실패가 나오는 조건

- 레거시 코드베이스 **전체**를 스펙화하려는 시도
- 30분이면 끝날 변경에 7단계 파이프라인 적용
- 일회성 프로토타입, 솔로·단기 프로젝트
- 탐색적 코딩 — 뭘 만드는지 아직 모르는데 조기 명세가 학습을 제약
- 요구사항이 자명한 단순 CRUD
- **팀이 실제로 스펙을 쓰고 리뷰하지 않는 경우** — 도구가 구해주지 않는다

### 결정 프레임

<pre class="mermaid">
flowchart TD
    A[새 기능 또는 시스템] --> B{AI 보조 사용? 또는 복잡한 요구사항?}
    B -- No --> C[애드혹으로 충분]
    B -- Yes --> D{장수 시스템? 유지보수자 다수?}
    D -- No --> E[Spec-First]
    D -- Yes --> F{코드 생성이 현실적?}
    F -- No --> G[Spec-Anchored: 대부분 여기]
    F -- Yes --> H[Spec-as-Source]
</pre>

**황금률:** 자기 맥락에서 모호성을 제거하는 데 필요한 **최소 수준의 명세 엄격도**를 쓸 것.

## 4. 숫자를 읽을 때 주의

> **DORA는 이 주제를 인정은 했지만 SDD 관련 연구 결과를 아직 발표하지 않았고, 동료평가를 거친 문헌에도 표준화된 지표가 없다.**

시중에 도는 "생산성 N% 향상", "결함 M% 감소" 수치는 거의 전부 도구 벤더의 마케팅 자료이거나, 단일 팀의 자체 보고이거나, 통제군 없는 전후 비교다. 위에 적은 75% 사이클 타임 감소 같은 인상적인 숫자도 1차 출처를 확인하고 어떤 베이스라인과 비교한 건지 따져봐야 한다.

자주 인용되지만 출처가 약한 대표적 예가 하나 있다.

> 개발자 800명 규모 제조업체에서 **주당 14만 달러 절감, 효율 25% 향상, 결함 15% 감소**

단서가 붙는다. 이 결과는 광범위한 교육을 동반한 정교한 구현에서 나온 것이지 "AI 제안을 전부 수락"해서 얻은 게 아니며, 결함이 오히려 줄었다는 점은 인간의 세심한 감독이 있었음을 시사한다. 1차 출처가 불분명하므로 참고용으로만 볼 것.

## 도구별 브라운필드 적합도

| 도구 | 성격 | 브라운필드 적합도 |
|---|---|---|
| GitHub Spec Kit | 4단계 CLI 워크플로, constitution 개념 | 보통 (`/speckit.converge`로 개선 중) |
| AWS Kiro | IDE 통합, EARS 표기법, 요구사항→설계→구현 | 낮음 (그린필드 설계) |
| OpenSpec | 경량 3단계, **스펙 델타** 중심, 도구 비종속 | **높음** |
| Tessl | spec-as-source, 코드는 재생성 대상 | 낮음 |
| BMAD | 에이전트 오케스트레이션, 무거움 | 낮음 (v6 알파) |
| Specmatic / Pact | 계약 테스트, 스펙-구현 일치 검증 | **높음** (기존 API에 바로 적용) |
