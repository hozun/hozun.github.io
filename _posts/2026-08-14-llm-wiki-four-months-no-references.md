앞서 [LLM Wiki 패턴](/2026/08/03/llm-wiki-pattern/)과 [매뉴얼 서비스에서의 판단](/2026/08/03/rag-vs-llm-wiki-ai-manual-service/)을 정리했다. 두 글 다 "패턴은 유효하지만 전면 도입은 하지 마라"로 끝났는데, 쓰고 나서 열흘쯤 지나 생태계 데이터를 다시 훑어봤다.

예상과 다른 게 나왔다. 도구는 계속 좋아지는데 **쓴 사람 이야기가 안 나온다.**

---

## 결론부터

**LLM Wiki는 개인 규모에서만 손익이 맞는 패턴으로 굳어지는 중이다.**

- Karpathy 게시트(4/4) 이후 4개월. 도구 쪽은 성숙했다 — OpenWiki는 한 달간 12번 릴리스했고, OKF v0.1 준수 리뷰도 통과했다.
- 그런데 **OpenWiki 주간 다운로드는 8월 첫째 주에 성장이 멈췄다.** 직전 4주 +119% → 그다음 주 +2.9%.
- HN 실사용 보고에서 **성공 사례를 수치와 함께 보고한 사람이 한 명도 없다.** 대신 유지비용 불만이 지배적이다.
- 공개된 case study는 100개 넘는 구현체를 통틀어 **전부 1인 프로젝트**다. 팀·회사 단위 배포에 비용·정확도 숫자를 붙인 사례가 없다.
- 경쟁 도구의 자체 벤치마크조차 결론이 "잘 튜닝된 vector RAG와 정확도 동률"이다.

패턴이 틀렸다는 뜻이 아니다. **적용 규모의 상한이 생각보다 낮다**는 뜻이다.

---

## 1. 4개월 타임라인

| 시점 | 사건 |
|---|---|
| 4/4 | Karpathy가 게시트 하나로 패턴 공개. stars·forks 각 5,000+ |
| 4월 중 | Google이 벤더 중립 규격 [OKF](/2026/07/14/google-open-knowledge-format-okf/) 발표 |
| 상반기 | Cognition DeepWiki(공개 저장소 50,000+ 인덱싱), Factory AutoWiki |
| 6/22 | LangChain openwiki 저장소 생성 |
| 7/9 | OpenWiki v0.1.0 공개 |
| 7/10 | OpenWiki Brains — Gmail·Notion·Git·X·HN·웹검색으로 소스 확장 |
| 7/16 | OpenWiki가 OKF v0.1 채택 (프론트매터 검증, 결정적 인덱스) |
| 8/4 | v0.3.0 — **생성 후 위키 내부 링크 검증 내장** |
| 8/11 | v0.3.2 — 의존성 취약점 패치, 코드 재구성 |

흐름만 보면 교과서적이다. 아이디어 → 규격화 → 상용 구현 → 오픈소스 CLI → 표준 준수 → 품질 도구 내장. 지난 글에서 "직접 구현할 때 필요하다"고 썼던 `lint` 단계(링크 유효성 검사)를 8/4에 OpenWiki가 내장했다. 도구 성숙도만 놓고 보면 불평할 게 없다.

문제는 이 타임라인 어디에도 **"어느 팀이 도입해서 이렇게 됐다"가 없다**는 것이다.

## 2. 채택 곡선이 꺾였다

npm `openwiki` 패키지 주간 다운로드다.

| 주 | 다운로드 | 증감 |
|---|---|---|
| 7/7–7/13 | 11,551 | — |
| 7/14–7/20 | 18,995 | +64% |
| 7/21–7/27 | 23,436 | +23% |
| 7/28–8/3 | 25,248 | +8% |
| 8/4–8/10 | 25,972 | **+2.9%** |

출시 후 4주간 두 배 넘게 늘다가 5주차에 평평해졌다. 8/11에 5,444로 튄 건 v0.3.2 릴리스 당일 효과고, 지속되는 상승은 아니다.

(주의: 7/12와 8/13이 0으로 기록돼 있다. 8/13은 집계 미완이고 7/12는 레지스트리 결측으로 보인다 — 앞뒤 일요일이 2,100~2,800대라 첫 주 합계는 실제보다 낮게 잡혔다. 즉 초반 증가율은 표보다 조금 완만하다.)

주간 2.6만 다운로드는 죽은 프로젝트의 숫자가 아니다. 저장소도 15.0K stars다. 하지만 **"시도해보는 사람"에서 "계속 쓰는 팀"으로 넘어가는 구간에서 멈춘 모양새**다. CLI 도구의 다운로드는 CI에 붙으면 매일 찍히기 때문에, 정착이 일어나면 오히려 완만하게라도 계속 올라야 한다.

## 3. 실사용 보고는 있는데, 전부 유지비용 이야기다

OpenWiki HN 스레드(96 points, 31 comments)를 열어봤다. 가장 눈에 띄는 건 **없는 것**이었다. 토큰 비용이나 정확도 개선을 수치로 보고한 성공 사례가 한 건도 없다.

있는 건 이런 쪽이다.

> "maintaining an LLM wiki has been a lot more effort than I thought, at least if we are trying to maintain a high quality in structure."

> "Wikis start out good, but either devolve in a journal-y mess after a while and many updates, or require constant expensive rewrites."

> "having verbose, duplicated, incorrect, outdated or incomplete docs often leads to worse performance for AI."

> "cruft unless there is a benchmark demonstrating it's actually better."

세 번째가 특히 중요하다. 지난 글에서 **지식 오염(knowledge poisoning)** 을 다루면서 "요약의 요약이 쌓이면 원본을 밀어낸다"고 썼는데, 여기서는 그게 이론이 아니라 **에이전트 성능 저하로 관측됐다**는 보고다. 낡은 위키는 없느니만 못하다는 것이 실사용자들의 공통된 관찰이다.

네 번째도 뼈아프다. 4개월이 지났는데 **"위키를 붙이면 이만큼 좋아진다"를 보여주는 공개 벤치마크가 아직 없다.**

## 4. case study는 전부 1인 프로젝트다

생태계를 정리한 awesome 목록을 보면 구현체가 100개를 넘는다. 데스크톱 앱, CLI 컴파일러, Obsidian 플러그인, MCP 서버, 파이썬 라이브러리까지 카테고리도 다양하다.

그런데 case study 항목의 성격이 일정하다.

| 사례 | 규모 |
|---|---|
| 개인 볼트 운영기 (수백 페이지 / 수백 커밋) | 1인 |
| 철학 아카이브 3,000페이지 단계적 인제스트 | 1인 |
| Obsidian second-brain CLI — "1,374명이 클론했다" | 1인 |
| 의료 연구 / 퀀트 금융 / 역사 OCR 파이프라인 | 각 1인 |

**전부 개인이다.** 팀 위키, 사내 배포, 규모별 비용 곡선을 다룬 사례가 목록에 없다.

한 가지 덧붙이면, 이 중 가장 구체적인 숫자가 붙은 운영기 하나는 1차 출처를 찾지 못했다. 큐레이션 목록의 요약에만 있고 원문이 검색에 안 잡힌다. 이런 것까지 감안하면 실증 기반은 더 얇다.

## 5. 왜 팀 규모로 안 넘어가는가

여기가 이 글의 본론이다. 네 가지가 겹친다고 본다.

### ① 개인 볼트는 피드백 루프가 닫혀 있고, 팀 위키는 열려 있다

<pre class="mermaid">
flowchart TB
    subgraph P["개인 볼트 - 루프가 닫힘"]
        P1[내가 소스 추가] --> P2[내가 컴파일]
        P2 --> P3[내가 읽다가 틀린 걸 즉시 발견]
        P3 --> P1
    end
    subgraph T["팀 위키 - 루프가 끊김"]
        T1[여러 명이 소스 추가] --> T2[CI가 자동 컴파일]
        T2 --> T3[PR diff를 아무도 정독하지 않음]
        T3 --> T4[틀린 내용이 그대로 축적]
        T4 --> T5[누가 고칠 책임인지 불명확]
    end
</pre>

개인은 자기가 만든 위키를 자기가 읽는다. 틀리면 그 자리에서 안다. 소유자가 한 명이라 수정도 즉시 된다.

팀은 다르다. 지난 글에서 "위키 갱신은 main 직접 커밋 말고 PR로 올려라"고 썼는데, PR로 올려도 **자동 생성된 문서 diff를 사람이 진지하게 읽지 않는다.** 코드 리뷰도 버거운데 매일 갱신되는 위키 200페이지를 검토할 리가 없다. 결국 승인 버튼만 눌리고, 오류는 조용히 쌓인다.

HN에서 나온 "journal-y mess로 변한다"가 정확히 이 지점이다.

### ② 유지비용이 규모에 선형이 아니다

문서가 N개면 링크는 최대 N² 방향으로 늘어난다. 개인 볼트 200페이지에서 잘 돌던 구조가 팀 위키 2,000페이지에서 안 도는 건 컴파일 비용 때문이 아니라 **일관성 유지 비용** 때문이다. 모순된 서술, 중복 문서, 고아 페이지가 규모의 제곱에 가깝게 늘어난다.

OpenWiki가 8/4에 링크 검증을 넣은 게 이 문제를 정면으로 건드린 것인데, 검증할 수 있는 건 링크가 끊겼는지까지다. **A 문서와 B 문서가 서로 다른 말을 하는지는 기계가 못 잡는다.**

### ③ 이득을 증명할 지표가 없다

RAG는 검색 품질을 재는 방법이 정립돼 있다. 위키는 그게 없다. "에이전트가 위키를 읽으면 더 나은가"를 재려면 같은 코드베이스·같은 태스크로 A/B를 돌려야 하는데, 공개된 게 없다.

지표가 없으면 팀 도입 결재가 안 난다. HN 댓글의 "benchmark 없으면 cruft"는 냉소가 아니라 **구매 결정을 하는 사람의 언어**다.

### ④ 코딩 에이전트가 이미 파일을 읽는다

이게 가장 근본적일 수 있다. 지난 글에서 "방법 3 — 그냥 파일로: 가장 저렴하고 놀랍도록 잘 동작한다"고 썼는데, HN에서 나온 질문이 똑같았다.

> "What does this do better than just asking your agent to 'write docs'?"

컨텍스트 윈도우가 커지고 에이전트의 파일 탐색이 좋아질수록, 별도 컴파일 파이프라인의 증분 이득이 깎인다. 위키 도구는 **에이전트 자체의 개선 속도와 경쟁**하고 있고, 이건 불리한 싸움이다.

## 6. 반대 신호도 있다 — 그런데 조건을 보면 같은 결론

토큰 절감을 실증했다는 논문이 하나 있다. *Knowledge Compounding: An Empirical Economic Analysis of Self-Evolving Knowledge Wikis*(Wen & Ku, 4월). 토큰을 소모재가 아니라 **자본재**로 보자는 주장이다.

| 항목 | 수치 |
|---|---|
| 4쿼리 누적 토큰 | 47K (compounding) vs 305K (RAG 베이스라인) |
| 절감률 | 84.6% |
| 30일 투사 — 주제 집중도 중간 | 53.7% |
| 30일 투사 — 주제 집중도 높음 | 81.3% |

지난 글에서 "위키가 싸지는 구간은 없다"고 단언했는데, 이 논문은 있다고 한다. 정정이 필요한가?

**전제가 다르다.** 논문이 꼽은 절감 메커니즘 세 가지 중 핵심은 "고가치 답변을 합성 페이지로 재활용"이다. 즉 컴파일된 페이지를 **캐시된 답변처럼 그대로 서빙**하는 구조다. 반면 지난 글의 모델은 매 쿼리마다 목차 → 문서 → 링크를 새로 도는 에이전틱 순회를 가정했다. 둘 다 맞는 말인데 측정 대상이 다르다.

여기서 재미있는 게 나온다. 매뉴얼 글에서 세운 규칙 ① **"위키는 근거가 될 수 없다"** 가 논문의 절감 메커니즘을 정확히 금지한다. 위키 문장을 그대로 답변에 실으면 안 된다고 못 박았으니, 싸질 수 있는 유일한 경로를 안전상 이유로 막은 셈이다. 결론은 오히려 강화된다 — **규제·안전 도메인에서 위키가 싸질 방법은 없다.**

그리고 "주제 집중도가 높을 때 절감이 커진다"는 조건 자체가 이 글의 논지와 맞는다. 주제가 집중된 소규모 지식 — 그게 개인 볼트다.

경쟁 도구 쪽 숫자도 비슷하게 읽힌다. Graphify가 71.5x 토큰 절감을 내세우지만, 비교 기준이 RAG가 아니라 **원본 파일을 그냥 읽는 것**이고(123K → 1.7K), 독립 출처 기준 방어 가능한 범위는 6.8x~49x다. 그리고 결론이 이렇다 — **"잘 튜닝된 vector RAG를 정확도에서 이기지 못하고 동률."**

## 7. 그래서 지금 무엇을 할 것인가

4개월치 데이터를 놓고 보면 판단이 이렇게 정리된다.

| 상황 | 판단 |
|---|---|
| 개인 지식 관리, 리서치 노트, 1인 사이드 프로젝트 | **해볼 만하다.** 루프가 닫혀 있어 손익이 맞는 유일한 구간 |
| 오픈소스 저장소 탐색·온보딩 | **DeepWiki를 쓰면 된다.** 직접 구축할 이유가 없다 |
| 팀 코드베이스 문서화 | **보류.** OpenWiki를 저비용으로 시험은 하되 프로세스에 넣지 말 것 |
| 고객 대면 서비스 (매뉴얼·상담) | **[지난 글의 결론](/2026/08/03/rag-vs-llm-wiki-ai-manual-service/) 유지.** 라우팅 층으로만 한정 |
| 규제·안전 도메인 | 합성 자체가 리스크. 원문 인용 구조를 벗어나지 말 것 |

팀 도입을 검토한다면 최소한 이 두 개는 먼저 만들어두라고 하고 싶다.

**1) 위키를 붙인 A/B를 자체적으로 돌려라.** 공개 벤치마크가 없으니 남의 숫자를 기다릴 수 없다. 같은 태스크 20개를 위키 있이/없이 돌려서 성공률과 토큰을 비교하는 정도면 충분하다. 이게 없으면 6개월 뒤에 "쓰는지 안 쓰는지 모르는 파이프라인"만 남는다.

**2) 위키 diff를 실제로 읽을 사람을 지정하라.** 지난 글에서 PR로 올리라고 썼는데, 그것만으로는 부족했다. **읽는 사람이 없는 PR은 main 직접 커밋과 같다.** 리뷰어를 못 정하겠으면 그건 위키를 유지할 여력이 없다는 신호다.

## 정리

- 도구는 성숙했다. OpenWiki는 한 달에 12번 릴리스했고 OKF 준수까지 갔다. 기술적 완성도 문제가 아니다.
- 그런데 채택 곡선이 5주차에 평평해졌고, 실사용 보고는 유지비용 불만이 지배적이고, 공개 case study는 전부 1인 규모다.
- 원인은 **팀 규모에서 피드백 루프가 끊기기 때문**이다. 자동 생성 문서의 diff를 사람이 안 읽으면 오류가 조용히 축적된다.
- 4개월간 "위키를 붙이면 이만큼 낫다"는 공개 벤치마크가 나오지 않았다. 이게 팀 도입을 막는 실질적 병목이다.
- 개인 규모에서는 여전히 유효하다. 절감을 실증한 논문의 조건(주제 집중도가 높을 때)도 정확히 그 구간을 가리킨다.
- 판단을 바꿀 신호는 하나다 — **팀 단위 A/B 결과가 공개되는 것.** 그때 다시 보면 된다.
