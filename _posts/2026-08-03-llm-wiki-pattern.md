## 결론부터

**LLM Wiki는 "검색해서 그때그때 답하는" RAG를 "미리 이해해서 문서로 남겨두는" 컴파일로 바꾸는 패턴이다.**

- 원천 자료(코드베이스, PDF, 웹페이지, 슬랙)를 **소스코드**로 보고, LLM을 **컴파일러**로, 링크된 마크다운 위키를 **빌드 산출물**로 취급한다.
- 에이전트는 벡터 유사도 상위 청크를 받는 대신, 사람처럼 **목차를 보고 → 문서를 읽고 → 링크를 타고** 들어간다.
- 이해가 **누적**된다. 질문할 때마다 원본을 다시 해석하지 않는다.
- 2026년 상반기에 Cognition DeepWiki, Factory AutoWiki, LangChain OpenWiki가 각자 같은 결론에 도달했다.
- 가장 큰 함정은 **지식 오염(knowledge poisoning)** — 요약의 요약이 원본을 밀어내는 현상이다. 설계에서 미리 막아야 한다.

이 글은 RAG를 한 번이라도 붙여본 사람을 대상으로, 개념 → 아키텍처 → 직접 구현 → 운영 함정 순으로 정리한다.

## 1. 왜 RAG로는 부족한가

RAG의 동작을 한 줄로 쓰면 이렇다.

<pre class="mermaid">
flowchart LR
    Q[질문] --> E[임베딩]
    E --> R[유사 청크 top-k]
    R --> C[컨텍스트에 붙여넣기]
    C --> A[답변]
</pre>

이 구조에는 세 가지 구조적 한계가 있다.

**1) 이해가 누적되지 않는다.** 100번 질문하면 100번 원본 청크를 다시 읽고 다시 해석한다. 어제 힘들게 알아낸 "이 서비스의 인증은 게이트웨이가 아니라 사이드카가 처리한다"는 사실이 어디에도 남지 않는다.

**2) 청크는 문맥을 잃는다.** 512토큰으로 자른 조각에는 "이게 전체 구조 중 어디쯤인지"가 없다. 함수 하나는 가져와도 그 함수가 어느 레이어에 속하는지는 모른다.

**3) 다중 홉 질문에 약하다.** "결제 실패 시 재시도 정책이 주문 상태에 어떤 영향을 주나"는 결제 모듈 → 재시도 큐 → 주문 상태머신 3단계를 이어야 한다. 유사도 검색은 각각의 조각만 가져오고 연결은 못 해준다.

GraphRAG가 3번을 해결하려 나왔지만, 대가가 크다. 실무 사례에서 **바닐라 RAG 대비 토큰 20배, 처리시간 2배** 수준이 보고된다. 그래프를 매 쿼리마다 순회하기 때문이다.

LLM Wiki는 방향을 튼다. **비싼 이해 작업을 쿼리 타임이 아니라 빌드 타임에 한 번만 한다.**

<pre class="mermaid">
flowchart TB
    subgraph RAG["RAG - 매번 재해석"]
        R1[질문] --> R2[검색] --> R3[해석] --> R4[답변]
    end
    subgraph GR["GraphRAG - 매번 재해석 + 비쌈"]
        G1[질문] --> G2[그래프 순회] --> G3[증거 융합] --> G4[답변]
    end
    subgraph LW["LLM Wiki - 이해는 빌드 타임에 끝남"]
        W1[소스] --> W2[이해/합성] --> W3[(위키)]
        W4[질문] --> W5[위키 탐색] --> W6[답변]
        W3 -.-> W5
    end
</pre>

## 2. 개념: LLM을 컴파일러로 보기

핵심 비유가 이 패턴의 전부다.

| 소프트웨어 빌드 | LLM Wiki |
|---|---|
| 소스코드 (`.c`, `.ts`) | 원천 자료 (repo, PDF, URL, 슬랙 로그) |
| 컴파일러 | LLM + 조사/합성 에이전트 |
| 빌드 산출물 (바이너리) | 링크된 마크다운 위키 |
| 증분 빌드 | git diff 기반 부분 재컴파일 |
| 소스맵 | 문장 단위 인용(citation) |
| 린트 / 테스트 | 구조 린트 + 신뢰도 감사(audit) |

여기서 반드시 지켜야 할 규칙이 하나 있다.

> **원천 자료는 절대 수정하지 않는다(immutable). 위키는 언제든 버리고 다시 만들 수 있어야 한다.**

빌드 산출물을 손으로 고치기 시작하면 재현성이 깨지는 것과 같은 이유다. 사람이 고치고 싶은 내용은 위키 본문이 아니라 **스키마 파일이나 소스 쪽에** 넣는다.

## 3. 아키텍처

실제로 돌아가는 LLM Wiki는 대체로 이 6개 요소를 갖는다.

<pre class="mermaid">
flowchart TB
    S["① Source Store (immutable) : raw/ — 원본 그대로, 해시 고정"]
    X["② Extractor : 주장 추출 + 출처 좌표(문서ID, 오프셋, 해시)"]
    W["③ Wiki (claim graph) : 양방향 링크된 마크다운, 주장마다 출처 연결"]
    T["④ Trust Registry : 주장별 검증 상태 추적"]
    D["⑤ Drift Detector : 주기적 재검증, 신뢰도 강등"]
    QL["⑥ Query Layer : 탐색 후 합성 (캐시 반환 아님)"]
    S -- ingest --> X
    X -- compile --> W
    W --> T
    W --> D
    W --> QL
    T --> QL
    D -. 재컴파일 요청 .-> X
</pre>

**① Source Store** — 원본 보관. 한 번 넣으면 안 바꾼다. 콘텐츠 해시를 같이 저장한다.

**② Extractor** — 원본에서 주장을 뽑되, 반드시 **출처 좌표**를 함께 남긴다. "문서 A의 1420~1580 문자 구간, 해시 `a3f9…`". 이게 있어야 나중에 검증이 된다.

**③ Wiki** — 실제 산출물. 개념(concept), 주제(topic), 참조(reference) 문서가 서로 링크된다. 원문 복사가 아니라 **합성**이다. 설명하고, 맥락을 붙이고, 교차 참조한다.

**④ Trust Registry** — 각 주장의 상태를 추적한다: `verbatim`(원문 그대로) / `paraphrased-unverified`(요약했으나 미검증) / `cross-confirmed`(복수 출처 확인). 신뢰도를 문서 프론트매터에 박아둔다.

**⑤ Drift Detector** — 주기적으로 주장을 현재 소스와 다시 대조한다. 불일치하면 신뢰도를 강등한다. 이게 없으면 위키는 조용히 썩는다.

**⑥ Query Layer** — 질문이 오면 캐시된 요약을 그대로 뱉지 않고, 위키를 탐색해 **신뢰도를 반영한 답**을 합성한다.

실무에서 ④⑤를 생략한 구현이 많은데, 6개월 뒤에 문제가 터지는 곳이 정확히 거기다.

## 4. 지금 쓸 수 있는 도구들

| 도구 | 대상 | 성격 | 특징 |
|---|---|---|---|
| **DeepWiki** (Cognition) | 공개 GitHub 저장소 | 호스팅 SaaS | URL의 `github.com`을 `deepwiki.com`으로 바꾸면 바로 열림 |
| **AutoWiki** (Factory) | 코드베이스 | 상용 플랫폼 | 저장소 변화 추적, 사람·에이전트 공용 문서 |
| **OpenWiki** (LangChain) | 코드베이스 + 개인 지식 | 오픈소스 CLI | git diff로 증분 갱신, GitHub Actions 연동, Gmail·Notion·Jira·Slack 소스 확장 |
| **llm-wiki** (nvk) | 임의 주제 | 오픈소스 플러그인 | 병렬 다중 에이전트 리서치, 주제별 격리 위키, Obsidian 호환 |
| **llm_wiki** (nashsu) | 개인 문서 | 데스크톱 앱 | 문서 드롭 → 점진적 위키 구축 |

빠르게 감을 잡고 싶으면 **DeepWiki**에서 익숙한 오픈소스 저장소를 하나 열어보는 게 제일 빠르다. 본인 코드베이스에 붙일 거라면 **OpenWiki**가 현재 가장 실무적이다 — CLI + CI 연동이 갖춰져 있고 산출물이 그냥 내 저장소 안의 마크다운이라 잠김이 없다.

코드가 아니라 **주제 지식**(예: 규제 조사, 경쟁사 분석)을 쌓는 게 목적이면 llm-wiki 계열이 맞다.

## 5. 직접 구현하기

도구를 쓰지 않고 직접 만들 때의 최소 구성이다. 사내 시스템에 붙이려면 결국 이렇게 된다.

### 5.1 디렉토리 레이아웃

```
knowledge/
├── raw/                    # ① 불변 원본
│   ├── 2026-08-01-arch-rfc.md
│   ├── 2026-08-02-incident-4471.md
│   └── manifest.json       # {파일: {해시, 출처URL, 수집일}}
├── wiki/                   # ③ 컴파일 산출물
│   ├── index.md            # 목차 (에이전트의 진입점)
│   ├── concepts/
│   │   ├── auth-flow.md
│   │   └── retry-policy.md
│   ├── systems/
│   │   └── payment-gateway.md
│   └── decisions/
│       └── adr-012-sidecar-auth.md
├── schema.md               # 사람이 소유하는 규칙 (LLM이 못 건드림)
└── .state/
    ├── trust.json          # ④ 주장별 신뢰 상태
    └── last-build.json     # 증분 빌드용 커밋 해시
```

`schema.md`가 중요하다. "이 위키는 이런 분류 체계를 쓴다", "결제 관련은 반드시 PCI 범위 표기" 같은 **사람이 정한 규칙**을 여기 둔다. 재컴파일해도 이 파일은 안 건드린다.

### 5.2 문서 포맷

```markdown
---
title: 재시도 정책
aliases: [retry, 재시도, backoff]
tags: [payment, reliability]
confidence: high        # high | medium | low
sources:
  - raw/2026-08-01-arch-rfc.md#L120-L138 (sha:a3f9c2)
  - raw/2026-08-02-incident-4471.md#L44-L61 (sha:7b1e08)
updated: 2026-08-03
---

## 요약

결제 재시도는 지수 백오프 3회, 최대 8초. 3회 실패 시
[[order-state-machine|주문 상태머신]]이 `PAYMENT_FAILED`로 전이한다.

## 상세

...

## 관련 문서
- [[payment-gateway|결제 게이트웨이]] ([결제 게이트웨이](../systems/payment-gateway.md))
- [[adr-012-sidecar-auth|ADR-012 사이드카 인증]] ([ADR-012](../decisions/adr-012-sidecar-auth.md))
```

링크는 **이중 표기**를 권한다. `[[wikilink]]`는 Obsidian이 그래프로 그려주고, 옆의 일반 마크다운 링크는 GitHub·에디터·에이전트가 그대로 따라간다. 둘 중 하나만 쓰면 어느 한쪽에서 링크가 죽는다.

`sources`에 **라인 범위와 해시**를 남기는 게 핵심이다. 이게 나중에 드리프트 검출의 유일한 근거다.

### 5.3 컴파일 파이프라인

```
1. ingest    원본 수집 → raw/ 저장 → manifest.json에 해시 기록
2. plan      전체 훑어보고 문서 목록/분류 결정 (index.md 초안)
3. compile   문서별로: 관련 raw 조각 모으기 → 합성 → 인용 부착
4. link      문서 간 참조 해석, 끊어진 링크·고아 문서 검출
5. lint      프론트매터 스키마, 링크 유효성, 중복 문서 체크
6. audit     주장 샘플링 → 원본과 대조 → trust.json 갱신
```

3번 컴파일 프롬프트의 뼈대는 이렇다.

```
너는 지식 컴파일러다. 아래 원천 자료로부터 "{문서 제목}" 문서를 작성한다.

규칙:
- 원문을 복사하지 말고 합성해라. 설명하고 맥락을 붙여라.
- 모든 사실 주장에는 [^출처ID] 각주를 달아라. 근거 없는 주장 금지.
- 이미 존재하는 문서는 재서술하지 말고 [[링크]]로 참조해라.
  기존 문서 목록: {index.md 요약}
- 원천 자료가 서로 모순되면 양쪽을 다 쓰고 confidence: low로 표시해라.
- 추측을 사실처럼 쓰지 마라. 모르면 "자료에 없음"이라고 써라.

원천 자료:
{인용 좌표가 붙은 raw 조각들}
```

마지막 두 줄이 실질적으로 품질을 가른다. LLM은 빈칸을 메우려는 성향이 있어서, **명시적으로 "모른다고 써도 된다"고 허가**해야 한다.

### 5.4 증분 갱신

전체 재컴파일은 비싸다. 코드베이스라면 git diff를 쓴다.

```bash
# 마지막 빌드 이후 바뀐 파일
git diff --name-only $(jq -r .commit .state/last-build.json) HEAD
```

바뀐 파일 → 그 파일을 `sources`에 인용한 위키 문서 목록 → 그 문서만 재컴파일. 역인덱스(소스 → 문서)를 빌드 때 같이 만들어두면 된다.

CI에 붙이면 이렇게 된다.

```yaml
# .github/workflows/wiki.yml
on:
  push: { branches: [main] }
  schedule: [{ cron: "0 18 * * 0" }]   # 주 1회 전체 감사

jobs:
  wiki:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: wiki compile --incremental
      - run: wiki lint --fix
      - run: wiki audit --sample 20        # 주장 20개 무작위 재검증
      - uses: peter-evans/create-pull-request@v6
        with:
          title: "docs: wiki 갱신"
          branch: wiki-update
```

**PR로 올리는 것**을 권한다. main에 직접 커밋하면 위키가 조용히 변하고, 아무도 diff를 안 본다.

## 6. 에이전트가 이 위키를 쓰게 만들기

위키만 만들어두면 에이전트가 알아서 읽지 않는다. 진입점을 명시해야 한다.

**방법 1 — 지침 파일에 박기** (`CLAUDE.md` / `AGENTS.md`):

```markdown
## 지식 베이스

코드를 수정하기 전에 `knowledge/wiki/index.md`를 먼저 읽어라.
관련 개념은 링크를 타고 들어가서 확인해라.
위키와 실제 코드가 다르면 코드가 맞다. 그리고 그 사실을 보고해라.
```

마지막 문장이 중요하다. **위키는 코드보다 낮은 권위**를 갖는다고 못 박아야, 낡은 문서가 잘못된 수정을 유도하는 사고를 막는다.

**방법 2 — MCP 서버로 노출**: `wiki_search`, `wiki_read`, `wiki_links` 세 개 툴이면 충분하다. 벡터 검색이 아니라 **전문 검색(grep/ripgrep) + 문서 읽기 + 링크 따라가기**로 구성한다. 에이전트가 사람처럼 탐색하게 두는 게 이 패턴의 요점이다.

**방법 3 — 그냥 파일로**: 코딩 에이전트라면 이미 파일을 읽을 수 있다. `knowledge/` 디렉토리를 저장소에 넣어두는 것만으로 절반은 끝난다. 가장 저렴하고, 놀랍도록 잘 동작한다.

## 7. 함정: 지식 오염

이 패턴의 가장 심각한 실패 모드다.

<pre class="mermaid">
flowchart LR
    O[원본 문서] -- 1세대 --> A[LLM 요약 A]
    A -- "2세대 (원본 대신 A를 참조)" --> B[LLM 요약 B]
    B -- "3세대 (원본은 아무도 안 봄)" --> C[LLM 요약 C]
</pre>

위키가 잘 만들어질수록 검색에서 원본보다 위키가 먼저 잡힌다. 그러면 다음 컴파일은 원본이 아니라 **직전 위키를 재료로** 삼는다. 요약의 요약이 쌓이면서 뉘앙스가 깎이고, 어느 순간 원본에 없는 내용이 "위키에 적힌 사실"이 된다. 되돌릴 방법도 없다 — 어디서 갈라졌는지 추적이 안 되니까.

현재 나온 도구들(DeepWiki, AutoWiki, OpenWiki) 대부분이 이걸 구조적으로 막지 못한다. "정확한 요약"과 "3세대 요약의 요약"을 구분하는 장치가 없기 때문이다.

방어책은 셋이다.

**1) 컴파일 입력에 위키 자신을 넣지 않는다.** 재컴파일은 항상 `raw/`에서 출발한다. 기존 위키는 "이미 있는 문서 목록"(중복 방지용)으로만 넘기고, 본문을 재료로 주지 않는다.

**2) 인용 좌표를 강제한다.** 출처가 `raw/` 안의 파일 + 라인 범위 + 해시로 해석되지 않는 주장은 린트에서 떨군다. 위키 문서를 출처로 삼은 주장은 애초에 통과 못 한다.

**3) 정기 감사.** 주장을 무작위 샘플링해서 현재 원본과 대조한다. 해시가 바뀌었는데 주장이 그대로면 `confidence`를 강등하고 재컴파일 큐에 넣는다.

## 8. 어디에 쓰고 어디에 쓰지 말까

**잘 맞는 곳**

- 큰 코드베이스에 신규 투입되는 사람/에이전트 온보딩
- 여러 문서에 흩어진 다중 홉 질문이 반복되는 도메인
- 원본이 자주 안 바뀌는 지식 (아키텍처, 규정, 도메인 규칙)
- 같은 질문을 여러 번 하는 팀 — 컴파일 비용이 분산된다

**안 맞는 곳**

- 실시간성 데이터 (재고, 가격, 대시보드 수치) — 그냥 API를 붙여라
- 원본이 하루에도 몇 번씩 바뀌는 경우 — 컴파일 비용이 이득을 넘는다
- 한 문서 안에서 끝나는 단순 조회 — 바닐라 RAG나 그냥 grep이 낫다
- 정확한 원문 인용이 법적으로 필요한 경우 — 합성 자체가 리스크다

비용 감각도 짚어두자. 초기 전체 컴파일은 한 번에 크게 든다(중형 저장소 기준 수십만~수백만 토큰). 대신 쿼리당 비용은 RAG보다 낮다. **질문 횟수가 많을수록 유리한 구조**다. 질문이 드물면 이 패턴은 손해다.

## 정리

- LLM Wiki는 이해를 **쿼리 타임에서 빌드 타임으로 옮기는** 패턴이다.
- 원본은 불변, 위키는 언제든 재생성 가능한 산출물로 취급한다.
- 모든 주장에 **출처 좌표(파일+범위+해시)** 를 붙이는 게 전부다. 이게 있으면 검증·증분갱신·오염방지가 다 따라온다.
- 시작은 가볍게: `knowledge/wiki/` 디렉토리 + `index.md` + 에이전트 지침 3줄. 벡터 DB도 그래프 DB도 필요 없다.
- 6개월 뒤를 생각한다면 신뢰도 추적과 드리프트 감지를 처음부터 넣어라. 나중에 붙이면 이미 오염된 위키를 상속받는다.
